# ADR 107: Reuse the local ChatGPT connection between bounded jobs

Status: implemented and released through PR 113 on October 12, 2026. Decision date: October 11, 2026. Owner-account login and replacement-worker reconnect passed. See the [release receipt](../operations/evidence/local-chatgpt-connection-20261012.json). Public customer onboarding remains unverified.

The owner requested one ChatGPT login for the supported local workflows instead of another device login for each imported batch. This supersedes ADR 068's prohibition on retaining the runner's own credentials between sessions. It does not extend a job, grant new tools, enable Windows coding, pool subscriptions, authorize paid fallback, or open general hosted subscription inference.

The official Codex client supports cached ChatGPT credentials and automatic renewal. See [OpenAI authentication documentation](https://learn.chatgpt.com/docs/auth). Keep the official client's own newly authorized cache separate from the desktop's cache and from the existing SIWC connection. These are different authorization protocols; do not reinterpret a Codex token as a SIWC token. New locally supported Codex workflows must reuse the common connection manager rather than introduce another login implementation.

Save the own-client cache in a separate per-Windows-user DPAPI-protected file under the existing app credential directory, outside every repository and outside cloud services. Restore it only into the existing trusted official-client worker's temporary authentication mount. Source/model children cannot read auth.json. Do not hide the complete CODEX_HOME directory: Codex stages its sandbox executable under CODEX_HOME/tmp, and the actual child cannot launch when that directory is masked. Preserve the independently checked credential-file, write and network denials.

The controller holds an exclusive credential-store lock during the session and checkpoints the official client's updated cache every fifteen seconds and before teardown. Official Codex owns token refresh. The application does not request another device code for a valid saved account. A saved but revoked account, storage failure, malformed cache, API-key authentication or changed account blocks work. An explicit disconnect removes only this runner connection locally. It does not claim server-side OpenAI revocation; users can revoke sessions in ChatGPT account security settings.

The existing thirty-minute comparison and four-hour personal-library deadlines remain fixed. Workers, transport broker and socket volume are removed on stop or expiry. Only encrypted connection credentials survive; evidence retention and app permissions keep their existing lifecycles. Hard controller/host failure can lose a recent refresh update and require reconnection. A single saved connection is not a promise to remain authenticated forever. Users may still need to reconnect after revocation, OpenAI policy changes or changing computers/accounts.

One connection can supply the existing eligible official-client analysis, topic synthesis and repository evaluation workflows. Coding may consume that connection only through a separately verified isolated adapter and an approved job. GitHub writes, publication, deployment and funding retain separate permissions. The website's WorkOS identity and the VibeScroll assistant plugin grant remain separate from permission to use a ChatGPT plan. Broader paid or remotely hosted SIWC eligibility remains gated as described by [OpenAI's plan-usage overview](https://developers.openai.com/siwc/token-sharing-open-source).

Verification includes one login across replacement workers, token-rotation persistence, wrong-account/API-cache rejection, revoked-account handling, storage failure, local disconnect and real Windows DPAPI protection. The Docker integration test uses synthetic credentials to prove encrypted retention, worker replacement and the actual official-client child credential/write/network denials without inference or credit use. It does not establish provider authentication, quota entitlement, model quality, live customer onboarding or production release. The first attempt to deny all of CODEX_HOME failed at sandbox launch and remains recorded in the implementation ledger.
