# ADR 155: return private Cloud frame pixels through existing assets

Date: October 25, 2026. Status: local implementation candidate. Production acceptance remains open.

## Evidence and decision

The protected production preparation export contains 18 speech segments and eight frame records. Each frame has bytes, dimensions, an ID, a SHA-256 hash and a timestamp. It contains neither JPEG data nor an app asset ID. Replaying that preparation through the serving 675dea2 Console displays older input rather than the retained speech. The PR182 renderer displays all 18 retained segments. This comparison uses an earlier production export, with older input replaced by a sentinel, and makes no fresh production request. It does not check transcription against the audio.

Keep the current authenticated MCP connection, source job, immutable preparation and private EU object storage. Add an optional `work_cloud_frame` tool for actual JPEG bytes during an active media lease. It accepts one canonical base64 string, at most 150000 decoded bytes, within the existing 262144-byte transport envelope. Hosts must compress larger samples before binding their hashes in preparation. It grants no new download, inference, task-launch or publication authority.

The action checks current account/grant/client/consent, task, generation, lease, rights, retention and preparation before storage. It verifies actual bytes, SHA-256, JPEG header dimensions and size, then repeats current authority checks after storage I/O. Registration and attachment commit together. Repeated uploads reuse the existing frame; concurrent duplicate objects and failed attachments enter the existing bounded deletion workflow. Existing quota accounting remains in force. No table, index, cron, queue or separate analysis store is added.

Store frame references under `personalMedia.cloudFrames`, with generation and preparation hash. Permit only this bound container through the existing Cloud-input exclusion for other personal-media workflows. Never change the accepted preparation, stored transcript or canonical analysis to add pixels. Reads reject retired assets, changed generations/preparations, rights loss and expired retention. The existing source expiry/redaction workflow owns physical deletion; its costs still need reservation.

The existing screenshot viewer, thumbnail, Home post projection and project source-content path consume these references. Cloud posts do not substitute earlier local frames when pixels are absent. Display adapters resolve exact `video_observation` speech and visual citations to transcript links or retained app images without changing stored citation IDs. A visual citation without pixels remains an observation. The browser diagnostic also observed a modal image remaining pending with lazy loading and decoding after switching it to eager. An explicitly opened evidence viewer now eagerly loads its selected image. A hydrated 320px citation click opens the modal and decodes that image.

## Provider mechanism and authentication

The current [official MCP Events documentation](https://developers.openai.com/plugins/build/mcp-events) supports webhook subscriptions in Work chats on ChatGPT web and desktop with Cloud selected. It requires MCP 2.0 discovery, an actual subscription, callback verification and signed delivery. ChatGPT manages subscription refresh. This validates the proposed provider mechanism; it does not prove this installation has subscribed, refreshed or executed an idle task. Tool refresh, actual subscription and a complete source-to-result run remain acceptance work. Desktop thread-management tools are not a public product API.

The [official OAuth documentation](https://developers.openai.com/plugins/build/auth) describes authorization-code OAuth with PKCE. In this implementation ChatGPT presents its connected user's bearer token to `/mcp`. The gateway verifies WorkOS JWT signature, issuer, audience, client, expiry and scopes. Convex verifies its registered JWT issuer and the backend performs a live WorkOS userinfo check. Database helpers independently require the active user, team membership and reviewed app grant. A Cloud lease additionally binds one source/generation, consent, task correlation, token hash and deadlines. The task ID is not a provider-attested identity. The host receives no database administrator credential. Subscription funding and app/database authorization are separate.

## Acceptance and limits

The [candidate receipt](../operations/evidence/launch-20261025-cloud-frame-return.json) records full offline checks, actual Console rendering, a locally generated JPEG decoding as both screenshot and thumbnail at 320px/desktop, and the protected export replay. These are local tests, not a fresh production post or audio-accuracy review. The registry audit reports two low and two moderate advisories, with no unresolved, high or critical findings.

The completed production post remains unchanged. Its old host files and lease references were cleaned up. This tool deliberately cannot reopen that expired/completed lease. Repairing that exact result still requires a separately bounded, current-authority acquisition/attachment operation that preserves its accepted analysis and verifies matching frame bytes. Do not overwrite the result or pretend a hash reconstructs a file. Source/audio comparison, production publication and actual mobile acceptance remain open.

The cumulative EUR5 ledger is unchanged: USD4.875014256044613 retained, USD0.424985743955387 unreserved under the USD5.30 working ceiling. No production call, deployment, video run, paid API inference or ledger write occurred for this candidate. The old fresh-source 9/10-call cost candidate excludes frames and existing analyzed lineage; it cannot clear this repair. Publication, acquisition, uploads, retries/unknown outcomes, retention and cleanup need a combined defensible reservation before dispatch. Full-main populated-index and provider/privacy/release gates remain. Preserve the reserved unanalyzed post and all original P/R/N/C/M acceptance.
