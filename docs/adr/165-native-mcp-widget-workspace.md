# ADR 165: add a native MCP widget around compatible Cloud commands

Date: October 26, 2026. Status: local implementation candidate, deployment and host acceptance pending.

## Decision

Build the owner-approved Library workspace, inline cited cards and project review board as a separate MCP Apps client. Preserve the serving-compatible `75fe204` Cloud/Events baseline. Add only the connection guide to the website. Keep the existing MCP command and source/job/lease authority; no new Cloud executor, copied library, paid fallback or subscription checkout is introduced.

Register three immutable single-file HTML resources and modern global/thread/file entrypoints. Add five bounded, authenticated read projections for minimal workspace discovery, state, browsing, topic evidence and private proposals. Recheck current grant, membership, source generation/revision and selected-project evidence. Never treat a deep link, file snapshot, mention or UI route as authority.

Use existing write commands for link saves, exact analysis requests, feedback corrections and private project suggestions. Sensitive settings, billing, privacy, organization edits and coding/publication approvals remain in the existing protected app until reviewed commands exist. The widget may deliberately send an exact-source user request into the active host conversation; the existing host flow owns execution. A source saved elsewhere does not gain a background execution bridge from this UI.

`MCP_WIDGET_ENABLED` defaults off and gates tool/resource registration in the frontend route. The matching Convex read projections must deploy before enabling it. Existing grants are neither widened nor renewed by the widget. Host support is detected and tested separately for ChatGPT and Codex; local rendering does not prove either host.

## Consequences

Public connection instructions and nine workflow skills can ship from one portable source package. Adding a raw server URL does not install those skills. The current registry contains public host registrations; universal self-service onboarding is not proved by adding one more local user fixture.

The widget has its own Operate design documentation. It does not replace the website DESIGN.md. Production resources are generated by `pnpm build:widget`; Vite fixtures remain development-only. Dependencies are pinned, with patched transitive overrides recorded in the implementation notes.

## Preserve deployed component identities

Set `autoInstallPeers: false` and `dedupePeerDependents: false` in the workspace. Declare the backend's existing Hono4.13.11 and React19.3.0 peers explicitly at the root, alongside its existing TypeScript and Zod versions. This keeps browser-only optional peers from changing Convex component paths. Do not remove upstream validators, rewrite component identifiers during deployment or relax the release guard. [pnpm documents cross-workspace optional-peer resolution and both settings](https://github.com/pnpm/pnpm/blob/main/pnpm/docs/settings/peer-dependencies.md).

The dependency fix changes no registry package version or integrity and restores byte-identical payloads and definition paths for all seven serving components. Frozen installation, exact offline comparison, types, focused integration tests, both production builds and the production audit verify different parts of this boundary. A fresh hosted preflight and actual-host acceptance remain required. This decision was formerly numbered162; the combined branch uses that number for finite app-Save intents.

See [implementation and plan coverage](../widget/implementation.md) and [rollout runbook](../operations/mcp-widget.md). The full acceptance matrix, production account evidence and public release gates remain open until actually verified.
