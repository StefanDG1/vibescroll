# ADR 189: enforce worker capacity in the job transaction

Date: October 29, 2026. Status: finite admission deployed at e9c3467; generous recurring owner policy is a local follow-up candidate.

The owner subsequently requested unlimited or generous personal usage. Use100 new analyses per UTC day and20 per hour for their authenticated account, with no artificial expiry or recurring sign-in. A revocable operator configuration selects this standing daily policy; other users' restrictions are unchanged. Initial extraction and retained-evidence reanalysis share the same daily counter. Ready-cache reads and idempotent requests remain free. Keep the existing short burst limit. This rate limit is not a monetary reservation or a promise of provider subscription capacity. Paid API fallback remains zero and Vercel must stay belowUSD20. The first finite10-job configuration was actually written and read back after the e9c3467 backend-only publication; the recurring policy is not live until the follow-up release/configuration succeeds.

The owner requests at least ten additional videos, excludes their ChatGPT subscription usage from cash budgeting and retains the Vercel ceiling below USD20. The previous USD0.17 per attempt was a conservative infrastructure hold, not an observed AI invoice. Preserve historical holds; report measured provider charges separately from reservations. No paid AI API or credit purchase is authorized.

Native Events tasks do not expose an atomic execution counter. A prompt that asks the model to update its own remaining budget already stopped a real job. Enforce a finite operator allowance in the same Convex mutation that creates each new media job. Share it across ordinary app approval, MCP requests and explicit retries. Identical queued replays, ready-cache reads and claims of an already-admitted job consume no additional slot. Failed approval rolls its debit back.

Use one bounded operator configuration, WORK_CLOUD_ADMISSION_JSON, with an immutable allowance ID, authenticated subject, maximum new jobs, start and expiry. Maximum configuration duration is seven days. Match the authenticated database actor, never a caller-supplied subject. Other accounts keep their existing hourly limit and all normal authorization gates. Invalid configuration fails closed. An expired or exhausted configured allowance refuses new jobs, while existing jobs and retained results remain accessible. Changing the count or expiry for the same ID cannot reset its counter.

Reuse the indexed limits table without a schema migration. Store the allowance expiry in its minute-valued window field so maintenance cannot remove an active allowance. The former hourly request counter stored hours in that minute-valued field, permitting premature cleanup. Store the hour start in minutes instead, preserving a current legacy count when updating it. Add no public operator mutation or parallel quota service.

Verify shared app/MCP denial, tenth admission and eleventh refusal, replay idempotence, expiry, malformed configuration, maintenance survival and legacy counter migration. Publish the compatible backend only after full checks and exact CI. Configure the owner's remaining allowance only after reconciling the separately admitted first TikTok. Native instructions may then process eligible saved intents until the server refuses admission, without editing prompt counters. This is operator-alpha capacity, not proof of general commercial host eligibility or ten successful production analyses.
