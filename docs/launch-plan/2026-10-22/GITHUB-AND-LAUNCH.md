## Repository deliverables

1. A compact opening: VibeScroll identity, one plain benefit, one legible actual-product image or short optimized animation, then Try example, Hosted app, Setup and Docs links. Provide descriptive alt text and a static image alternative.
2. An understandable workflow: save, cited insight, optional project decision, editable plan and separately approved action. Include a real no-fit/already-implemented example.
3. A capability table with available, private pilot, planned and externally gated labels. State supported source types and companion platforms precisely. Verify claims against exact-commit evidence.
4. Two honest starting paths: hosted use and a clean local synthetic demo. Separate a personal live setup guide and self-hosting guide with the actual services, credentials, persistent storage and recovery obligations. No unsupported one-click claim.
5. A small architecture diagram showing browser, Convex, source preparation, user's companion, model provider and isolated cloud execution. Show credential/privacy boundaries and explain that local preparation can send evidence to a provider.
6. Clear service-versus-code explanation: preserve MIT and upstream notices, document bundled third-party terms, explain paid hosting/setup/support and the limits of self-hosting. Do not relicense existing foundation or frozen skill snapshots.
7. Reconcile root and docs CONTRIBUTING/SECURITY entry points. Give reproducible commands, a map of the code, safe issue reporting and a verified private security route. Preserve historical evidence instead of turning dated status into current claims.
8. Review existing bug and PR templates. Add a focused feature request and setup/support route if needed. Ask for safe diagnostics, expected/actual behavior, version and reproduction, never credentials or private transcripts.
9. Prepare a community conduct policy and contribution expectations appropriate to a small maintained project. Document triage, issue labels and maintainer review. Add a few genuinely scoped contributor tasks only after verifying they exist; do not create fake activity.
10. Publish an honest roadmap and readable release notes tied to immutable versions and exact-commit CI. Include migration/recovery notes where necessary. Badges must reflect real checks. Avoid a wall of decorative counters.
11. Prepare repository metadata: plain description, verified homepage, relevant non-spam topics and a social-preview image. Candidate topics include knowledge-management, video-analysis, mcp, productivity, nextjs and convex when accurate. Metadata edits and enabling Discussions are external actions requiring the preflight decision.
12. Prepare reusable public assets under a small repository-owned documentation directory: light/dark screenshots, social card, demo poster and text transcript. Keep heavy video outside the Git history where appropriate and provide an accessible link. Strip private project names, source archives, account details and signed URLs.

[GitHub's community-profile guidance](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories) provides a check for contribution entry points. [Repository topics](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics) support discovery. Recheck these controls before changing settings.

Another person can follow the fresh-clone synthetic demo using the documented versions. Read it at narrow width and in GitHub light/dark appearance. Verify links, media size, alt text, canonical URLs, license attribution and secret scans. A local fixture demo must say so.

## Recruitment, learning and first purchases

Ask each prospect to show a recent practical save, where it went and whether they used it. Observe current workflows and paid alternatives before showing VibeScroll. Start with the forgotten-save session and a concrete source-to-decision example.

Invite ten people who have three permitted sources and an active project. Run five observed sessions, repair repeated failures, then five independent sessions. Track signup, saved source, route chosen, ready output, evidence opened, decision reviewed, plan retained/exported, return use and actual purchase/decline. Record correction burden, failures, support time and processing cost without collecting private content in analytics.

Four of five independent completions is a proposed operational signal to try another small cohort, not a market benchmark. If people do not return, investigate before expanding acquisition. Three actual buyers would be useful early evidence, not product-market fit. Honest no-fit results count as decisions, not failed opportunities to generate code.

Test the existing monthly catalogue after a relevant output and verified billing readiness. Prepare a three-year founding-pass worksheet covering net revenue, included storage/support/updates/processing, obligations and overage. The owner selected testing it after the pilot. No price or unlimited allowance is adopted here.

Later experiments include an opt-in source-to-decision clinic, a creator-approved starter collection, an already-built challenge and a matched comparison against bookmarks plus an assistant. Measure qualified users and repeat use. Do not treat public post impressions or stars as customer validation.
