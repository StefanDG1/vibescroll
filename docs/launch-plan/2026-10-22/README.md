## The core experience

1. A visitor sees the actual Library style and an approved example without an account. The example connects a source, citations and a project decision. Label synthetic content and compressed waiting time.
2. After sign-in, ask what the person hopes to do with saved material. Offer library-first and active-project paths. Keep the purpose editable.
3. Explain only the permissions needed now. Connect an eligible route or show a precise repair. GitHub and bulk import remain optional before first value.
4. An explicit saved link promptly receives a durable status. Automatic extraction uses a previously reviewed grant. Save-only remains available.
5. The result shows a short summary, distinct insights, evidence references, coverage and uncertainty. Users can correct and file it without re-running inference.
6. Optional project review shows current context, relevance, evidence and alternatives. Keep no-fit, already-implemented, deferred and insufficient-context outcomes.
7. Retain an editable private plan and export. Coding, spending, final patch approval and draft PR publication retain their existing separate boundaries.
8. Returning Home presents the last useful result, a waiting item or unfinished decision. Preserve Library search, Tree/Folders and remembered navigation. Start with a compact return area; do not add an unrelated engagement dashboard.

## Local and cloud processing

Reuse the optional paired companion. The web application remains usable without installation. Support the verified platform first, with preflight, guided pairing, the user's supported official account, a real sample job, visible health, pause/unpair and redacted diagnostics. Offer startup at sign-in only by explicit choice. Independent local acceptance requires a different person's account and device.

A phone submission may wait for an available paired laptop. Being powered on is not enough if the worker, engine, account or quota is unavailable. Do not promise wake-up of sleeping hardware or proactive messages in a finished assistant conversation without actual host support.

Explain what stays on the computer and what evidence reaches a model provider. Never pool the founder's subscription or describe local preparation as entirely offline AI. The official OpenAI interest application has been submitted; commercial customer eligibility remains unconfirmed. A supported cloud route can serve eligible testers with explicit reservations and limits. Never silently switch to paid processing.

Cloud subscriptions can include a processing allowance. Display its unit, estimate, maximum, holds, settled usage and remaining balance. Reuse valid prepared evidence on a retry. Coordinate local and cloud claims so one intent is not processed twice. Keep service fees, provider limits and processing charges distinct.

## Design and onboarding

The current Library is the visual authority. Preserve its cool surfaces, mint selection, icon-led evidence, typography, Tree/Folders behavior and familiar navigation. Use the existing original Scroll character for a brief explanation or genuine completion feedback. Check small-size recognition before adding it widely.

Extend the same treatment across every screen, public page and help illustration. Respect device-following appearance and explicit light/dark selection. Keep five mobile actions: Home, Library, Save, Projects and Account. Do not force a new theme at purchase or add artificial processing screens.

Provide a complete resumable setup journey, with a short first-result path and an optional full guided route. Steps include purpose, first source, route, assistant scope, pairing, project, saved-link import and advanced preferences. The next incomplete step gets one primary action and a relevant help link. Import previews distinguish links, acquired evidence and completed analysis, and require explicit scope and budget for batches.

Acceptance includes 320/390/768/1440 CSS-pixel widths, large text, keyboard, focus, touch, reduced motion, long titles, empty/sparse/deep/wide libraries, network interruption and changed permissions. Physical-device and independent-human checks are separate evidence.

## Public collections, reuse and the globe

Build personal usefulness before depending on a network. Create explicit public editions with provenance, a useful no-signup reading experience, save-to-my-library, reporting, corrections and removal. Seed a small permitted founder-curated collection and support creator-partnered collections later. Publication authority is distinct from private/team sharing.

Separate reusable source-level extraction from private notes, goals, project context and decisions. Reuse needs compatible content revision, language, pipeline/schema and coverage, plus a verified permission basis. A URL alone is not a cache key. Preserve corrections, deletion propagation and stale-artifact invalidation. Private activity must not leak through cache existence or timing.

Prefer eligible derived-artifact reuse over permanent video hosting. Raw-media acquisition, caching and redistribution require separate rights/provider evidence. Unsupported retrieval stays visibly unavailable rather than bypassing access controls.

The globe uses voluntary coarse sharing locations, aggregate thresholds and no inferred device/IP location. Provide topic/list alternatives, withdrawal, reduced motion and lazy rendering. Build and test the module with labelled fixtures; enable real public discovery only when the necessary contributions and controls exist. Do not present fixture activity as customer traction.

## Customer and open-source launch

Keep the brand line "Make scrolling useful." Test "Turn what you save into your next project decision" as a supporting message. Use actual customer language after interviews. Avoid superiority, accuracy, time-saving, unlimited-access or revenue promises without evidence.

Prepare a legible source-to-decision example, a captioned 30-45 second actual-product overview, a deeper setup walkthrough, screenshots in both themes and an accessible static fallback. Public pages should explain the benefit before detailed architecture. Add visible GitHub links to website navigation/footer, the open-source explanation, approved launch materials and relevant demos.

The repository is a product entry point. Improve its README, demo assets, fresh-clone path, self-hosting explanation, contribution/security documents, metadata, releases and issue templates. Retain upstream notices. A clear hosted-versus-self-hosted comparison must list dependencies and limits. Open source does not imply every third-party hosted component is free or offline.

Recruit twenty qualified contacts to invite ten testers. Run five observed sessions, repair repeated failures, then five independent sessions. Ask for three permitted saved sources and one project. Record first useful output, evidence inspection, decision/plan retained, return use, support time, failure/correction burden, route cost and payment decisions. Proposed cohort thresholds guide a next small test; they are not market benchmarks.

Prepare a first GitHub release announcement and distribution package for personal builder contacts, appropriate communities, Peerlist, BetaList, Product Hunt and a genuinely tryable Show HN when eligible. Verify venue rules at posting time. HN requires founder-authored writing under its current rules. TrustMRR comes after real revenue and a separate decision about integration access. No paid boosts, bought stars, automated mass promotion or vote exchanges.

Keep monthly pricing as the first purchase test. Evaluate a three-year hosted pass after measuring net revenue, support, storage and processing obligations. Specify dates, allowance and overage behavior; three years is not lifetime. Prepare the offer model and cost worksheet now, but do not invent a validated price or launch live charges.
