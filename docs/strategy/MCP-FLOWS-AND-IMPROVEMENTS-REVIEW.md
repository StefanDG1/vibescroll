# MCP flows and improvement plan

Status: core scope approved for implementation under R137 on November 1, 2026, Europe/Berlin. The owner requests completion of all core phases. Additional suggestions are excluded and saved separately. Existing monetary/provider/publication boundaries still apply. Follow the [execution ledger](MCP-FLOWS-IMPLEMENTATION.md) for progress and acceptance; source, tests and production remain distinct.

## Outcome and baseline

A person should be able to connect once, save or find a post, understand its actual analysis state, apply its saved insights to a project, discuss a plan, approve one exact issue and see work feedback. The website and an assistant should operate on the same durable records.

Website68ae312 and backend1f96e6d are the accepted baseline. The public docs already have eight pages, three diagrams, search and53generated full-feature descriptors. Nine end-user skills exist in the source package; installation in the owner's custom host has not been established. Automatic native prepared analysis, paid-credit processing, shared reuse, versioning and the proposal/issue loop already exist with their recorded acceptance limits. This plan improves and verifies those paths; it does not propose rebuilding them.

The five previously selected priorities remain in scope: fresh-user sandbox acceptance, monetary provider reserve/settlement, payment/progress/failure UX, fresh-chat MCP acceptance and issue/PR outcome feedback. The phases below place them alongside the MCP/documentation improvements rather than creating a second competing roadmap.

## Organize documentation by flows, with skills as a second view

Use three connected ways to navigate:

1. **What you want to do:** user workflows, normal examples, progress, costs and recovery. This is the primary navigation.
2. **What the assistant can call:** grouped tool reference, exact schemas, outputs, side effects and availability. Preserve an alphabetical index and permanent tool anchors.
3. **How the assistant follows the workflow:** skills, tool descriptions, Events and host support. Map each skill to its workflows/tools. Do not make skill installation a prerequisite for reading the docs.

Do not rename or remove existing MCP tools just to improve the documentation grouping. A tool has one primary reference group and may be linked from several workflows. Skill names are tags, not the source of truth for tool capabilities.

## Testing strategy

1. **Contract fixtures:** inputs, outputs, safe errors, examples, old/new formats, pagination, stale versions and funding-route distinctions. Generate docs from these where appropriate.
2. **Isolated backend:** two simultaneous same-post requests, replayed starts/completions, grant revocation, user/team isolation, cache hits, payment risk, quote expiry and unknown settlement. No production spend is needed for race testing.
3. **Model behavior:** test tool discovery and actual choices, not only direct function calls. Include vague link requests, already-ready posts, no-fit projects, save-only requests, missing repository context and malicious source instructions.
4. **Host matrix:** original custom ChatGPT connection, fresh ChatGPT chat, installed plugin skills where available, Codex and a text-only MCP client. Record tools-only support separately from skills/Events/image/embedded-UI support.
5. **Fresh-user sandbox:** checkout/wallet → save/cache or bounded analysis → proposal → explicitly approved test issue → feedback. No real card charge; stage provider outages and signed webhook replay.
6. **Browser:** public docs search, deep links, mobile navigation, diagrams and disclosure controls; preserve accepted Home and Library Tree/Folders geometry. Serialize browser interaction and assert the exact route before inspecting controls.
7. **Production canary:** only after local/exact CI and current gates pass. Prefer retained evidence and existing results, reuse the original connection, retain failed/unknown receipts and report source/local/staging/production/independent acceptance separately.

Performance targets are set after the baseline. Cache reuse, stale-state behavior and p95 whole-flow latency matter more than a single warm happy-path number. No made-up speedup, per-tool Convex price or unlimited subscription allowance is an acceptance criterion.

## Decisions to review

| Decision                             | Recommended direction                                                                         | Alternative and trade-off                                                                                                                 |
| ------------------------------------ | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Docs navigation                      | Flows first, grouped tools second, skills as tags/cross-links                                 | Skills-first assumes users know what is installed and splits shared actions across several pages.                                         |
| In-chat plan generation              | Host reasoning plus `save_project_proposal`; API generation only when chosen                  | Automatic API generation is more uniform across hosts but spends credits when the chat could write the plan.                              |
| Prepared video inside an active chat | Run a bounded supported-capability investigation after core reliability/funding work          | Prioritizing it earlier may simplify the experience sooner, but host image/execution support and background automation cannot be assumed. |
| Reference detail                     | Concise normal view, expandable schemas/worker internals, exact advanced reference            | Showing every protocol/worker field up front improves immediate completeness but overwhelms normal users.                                 |
| Version selection                    | Owner-controlled model policy and evidence compatibility, retain candidate/incumbent/rollback | Automatically choose a nominally stronger model; simpler wording but unsupported quality assumptions.                                     |

Approval should select priorities and resolve material choices. It is not a new blanket permission for purchases, real charges, unsupported hosted subscription use or arbitrary public issue publication. Routine compatible releases remain delegated within the existing actual gates once the plan is approved.
