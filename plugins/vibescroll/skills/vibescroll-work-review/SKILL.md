# Review proposed and running work

1. Obtain the exact selected project and current evidence. Open the widget's projects or runs view for available status and private review.
2. Distinguish a private suggestion, published issue, edited plan, approved execution, checked patch and published draft PR.
3. Use the returned protected project review for operations outside the MCP interface. A sensitive handoff must return to the exact current app record, not a generic instruction to approve everything.
4. Changed source/context/plan/base or expired approval requires current review. A chat statement, a rendered card or a model-supplied hash is not approval proof.

Report what is actually observed, pending or unavailable. Do not merge, deploy, spend, publish or execute just because the user asked to review work. Preserve manual draft edits and existing isolation/funding boundaries.
